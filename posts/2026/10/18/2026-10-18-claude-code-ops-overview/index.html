Claude Code 운영기

  1. Hermes Agent 대신 cron과 claude -p를 씁니다

2026년 10월 기준입니다. Claude Code 2.1.300과 Dagu 2.18.2에서 확인했고, Hermes Agent 평가는 2026년 7월, 약관과 공식 문서는 2026-10-06에 확인했습니다.

올여름 집 서버에 오픈소스 에이전트 Hermes Agent를 상주시켰다가 열흘 만에 걷어냈습니다. 제 용도에서 Hermes가 해 준 일 중 남은 것은 cron뿐이었습니다. 지금은 Max 구독 하나로 스케줄러 Dagu가 claude -p를 돌리고, 할 일은 이슈 트래커 티켓으로 적고, iPhone에서는 원격 제어로 서버의 Claude Code 세션을 엽니다.

이 글은 왜 걷어냈고 그 자리에 무엇이 들어갔는지를 한 편에 그린 것입니다. 설정 파일과 함정까지 적으면 길어져서, 이 글은 구성과 그렇게 한 이유까지만 다룹니다.

Hermes Agent에서 얻은 것은 cron뿐이었습니다#

Hermes Agent는 서버에 상주하면서 크론으로 일을 돌리고 메신저로 대화하는 에이전트입니다. 7월 13일에 환경을 만들기 시작해 22일에 띄웠고, 맡긴 일은 아침 브리핑 둘(어제의 티켓 변화, 밤새 쌓인 글)을 Discord로 보내는 것과 iPhone에서 Discord로 말을 걸면 답하는 것이었습니다.

이틀 뒤에 「cron 말고 뭐가 다르냐」는 생각이 들었고, 코드를 열어 보니 실제로 그랬습니다. 브리핑 스크립트가 티켓 조회부터 마크다운 조립까지 다 끝내서 stdout에 완성품을 내놓고, Hermes의 LLM은 그 결과를 문장 몇 줄로 다시 풀어 쓰는 일만 했습니다. Hermes가 해 주던 일은 넷인데, 셋은 이미 갖고 있던 것으로 되는 일이었습니다.

  • 정해진 시각에 잡 돌리기 cron이면 됩니다. 나중에 Dagu로 바꿨습니다.
  • Discord로 보내기 이미 있던 웹훅 릴레이가 합니다.
  • 정리된 데이터를 문장으로 풀어 쓰기 claude -p 한 번이면 되고, 품질은 이쪽이 낫습니다.
  • iPhone에서 말 걸면 답하기 이것만 당시에 대신할 것이 없던, Hermes라서 되는 일이었습니다.

그 하나도 오래가지 못했습니다. 7월 22일에 에이전트가 티켓에 손을 대는 사고가 한 번 난 뒤 트래커 권한을 읽기와 댓글로 묶었고, iPhone에서 시킬 수 있는 일이 「읽고 말하기」만 남았습니다. 남들이 쓴 기록을 찾아봐도 비슷했습니다. 몇 주 뒤에도 쓰고 있다는 후기는 찾지 못했고, 게이트웨이 메모리가 400MB에서 20~37GB까지 자라 OOM으로 죽는 이슈가 여럿이었습니다.

다만 이것은 제 쓰임새에 한한 얘기입니다. 남들이 꼽는 Hermes의 강점은 스킬을 스스로 만들고 메모리를 쌓아 가는 쪽인데, 저는 그 기능을 꺼 두고 정해진 시각에 알림 보내는 일만 시켰습니다. 아침 브리핑처럼 정해진 시각에 뭔가를 보내는 용도라면 Hermes를 띄울 이유가 거의 없습니다. 스킬을 쌓게 두는 용도는 안 해 봐서 모릅니다. 7월 24일에 컨테이너를 내렸고, 스크립트는 그대로 둔 채 호스트에서 돌리기만 하면 됐기 때문에 잃은 것은 없었습니다.

걷어낸 자리에는 cron과 claude -p가 들어갔습니다#

브리핑 스크립트는 호스트의 cron으로 옮기고, 결과를 문장으로 풀어 쓰는 일은 claude -p가 맡게 했습니다. 컨테이너 안의 에이전트가 사라지니 프롬프트와 수집 스크립트가 전부 레포로 나왔고, 구독 로그인 세션을 그대로 쓰니 API 요금이 붙지 않았습니다. 대신 조건이 하나 생겼습니다. claude -p는 홈 디렉터리의 구독 로그인 세션을 읽기 때문에 호스트에서만 돕니다. 컨테이너에 넣으면 그 세션이 없습니다.

cron으로 돌려 보니 세 가지가 걸렸습니다.

  • 안 돌아도 아무도 모름 실패하면 알림이 오지만 아예 안 돈 경우는 조용합니다. 서버가 꺼져 있던 날의 실행은 그냥 사라지고, 다음 날 아침에야 「어제 브리핑이 없었네」 합니다.
  • 겹치지 않게 하는 수단이 시간차뿐 브리핑 잡을 10분씩 떨어뜨려 놓은 것이 전부인데, 앞 잡이 10분 안에 끝난다는 보장이 없습니다. LLM을 태우는 잡은 걸리는 시간이 들쭉날쭉해서 이 전제가 특히 잘 깨집니다.
  • 기록이 안 남음 언제 얼마나 걸렸고 무슨 출력을 뱉었는지 남지 않아, 문제가 생기면 매번 SSH로 들어가 파일을 뒤졌습니다.

cron은 일주일 만에 Dagu로 바꿨습니다#

후보부터 걸렀습니다. Airflow가 잘하는 것은 잡 사이의 의존 관계, backfill, task 간 값 전달인데 제 잡 스무 개 중 서로 의존하는 것은 하나도 없었고, 가만히 있어도 2GB를 먹으면서 컨테이너로 떠서 claude -p가 안 됩니다. Kestra, Windmill, Prefect, Dagster도 같은 이유로 접었습니다. 남은 것이 Dagu였습니다. Go로 짠 16MB 단일 바이너리를 호스트에 놓고 실행하면 끝이고, DB도 메시지 브로커도 없습니다.

cron에서 걸리던 셋이 이렇게 풀렸습니다.

  • 큐 같은 큐에 묶인 잡은 한 번에 하나만 돌고, 겹치면 실패도 건너뛰기도 아니라 기다립니다. 10분 시간차와 flock을 한꺼번에 대신합니다.
  • catchup 서버가 꺼져 있어 놓친 실행을 부팅 뒤 정해 둔 시간 안에서 한 번 돌려 줍니다.
  • 실행 기록 언제 돌았고 얼마나 걸렸고 무슨 출력을 뱉었는지 웹 화면에 남습니다. 로그 뒤지러 서버에 들어갈 일이 줄었습니다.
  • 잡 하나가 파일 하나 스케줄 변경이 git diff로 남고, 옮길 때 기존 명령을 run: 아래 그대로 넣으면 됩니다. 스크립트는 한 줄도 안 고쳤습니다.

대신 큐로 묶으면 전체가 끝나는 시각이 뒤로 밀리고, crontab 한 줄이 YAML 파일 하나가 됩니다. 잡이 몇 개 안 되면 손해입니다. 손으로 한 번 돌린 실행이 다음 날 정기 실행을 삼킨 것 같은 삽질은 그때 글에 있습니다.

지금은 Dagu가 매일 아침 브리핑 일곱 개와 개인 위키 갱신 하나를 claude -p로 돌립니다. 위키 갱신은 전날 커밋과 티켓 코멘트를 읽어 저에 대한 위키에 반영하는 잡이고, 서버 소프트웨어를 올리기 전에 릴리스 노트를 읽고 막을지 답하는 검토는 별도 러너가 띄우지만, 부르는 것은 같은 claude -p입니다.

Dagu는 잡 하나를 YAML 파일 하나로 적는 스케줄러이고, 제 잡 정의는 아래처럼 생겼습니다. claude -p를 부르는 잡은 전부 같은 큐에 넣어 한 번에 하나만 돌게 하고, 사람이 없는 시각이라 실패하면 재시도 뒤 알림이 옵니다. 예약 잡이 끝나도 남는 MCP 프로세스, 상위 레포의 CLAUDE.md가 예약 잡에 따라 들어오는 문제, 최소 권한으로 돌리는 구성은 이 글에서는 넘어갑니다.

구독 로그인으로 claude -p를 예약 실행해도 되나#

됩니다. 약관 문장만으로는 판단이 서지 않아 공식 문서까지 직접 열어 확인했습니다. Consumer Terms는 봇이나 스크립트로 서비스에 접속하는 것을 금지하면서 「API 키로 접속하는 경우」와 「Anthropic이 명시적으로 허용하는 경우」를 뺍니다. 무엇이 명시적 허용인지는 약관이 아니라 Claude Code 문서에 있습니다.

공식 문서는 구독 로그인으로 사람 없이 돌리는 길을 직접 안내합니다. Authentication 문서는 CI와 스크립트용으로 claude setup-token으로 1년짜리 구독 토큰을 만들라고 적고, GitHub Actions 문서는 그 토큰으로 돌리면 API 과금 대신 구독 사용량에서 빠진다고 적습니다. 헤드리스 문서는 예약 잡에서 --permission-prompts none을 쓰라고 안내하고, Legal and compliance는 수정하지 않은 바이너리에 본인 구독으로 로그인하는 것을 막지 않는다고 못 박습니다.

같은 문서에 사용 한도는 개인이 보통 쓰는 정도를 기준으로 잡았다는 문장이 있어서, 예약 잡의 호출은 하루 스무 번 안팎으로 둡니다.

로그인 방식은 둘 중 하나입니다.

  • /login 결과 서버에서 한 번 로그인한 결과를 그대로 씁니다. 기본은 이쪽입니다.
  • setup-token 토큰 브라우저를 열 수 없는 곳에서는 claude setup-token으로 만든 토큰을 씁니다.

다만 Authentication 문서에 따르면 setup-token 토큰은 모델 요청만 할 수 있어서 claude.ai 커넥터와 원격 제어는 못 씁니다. 아래에서 말할 티켓 커넥터를 세션에서 쓰려면 /login 쪽이어야 합니다.

주의할 변화가 하나 있습니다. 헤드리스 문서는 --bare가 앞으로 -p의 기본값이 된다고 적었고, --bare는 /login 결과와 CLAUDE_CODE_OAUTH_TOKEN을 읽지 않습니다. 그 버전이 나오면 구독 로그인으로 돌던 잡이 인증 실패로 멈추므로, CLI를 올릴 때 변경 기록에서 이 항목을 확인합니다.

iPhone에서는 Discord 대신 Claude 앱으로 서버 세션을 엽니다#

Hermes만 하던 「iPhone에서 말 걸기」는 Claude Code의 원격 제어가 맡았습니다. 밖에서는 Claude 앱으로 서버의 Claude Code 세션을 쓰고, 켜 둔 것은 둘입니다.

  • 이어 보기 터미널에서 연 세션은 remoteControlAtStartup 설정으로 전부 원격 제어가 붙게 해서, 자리를 떠도 iPhone에서 이어 봅니다(설정 글).
  • 새로 열기 서버의 tmux에는 claude remote-control 서버 모드를 띄워 두어 iPhone에서 새 세션을 엽니다(서버 모드 글).

서버 모드를 띄우면 터미널에 이렇게 뜹니다. 이름과 주소만 자리표시로 바꿨고 나머지는 화면 그대로입니다.

이 상태로 두면 Claude 앱의 코드 탭에 이 서버가 기기로 나타나고, 폴더를 고르면 그 서버에서 새 세션이 시작됩니다.

Hermes 때와 다른 점은 iPhone에서 말을 거는 상대가 매일 쓰는 Claude Code 세션 그대로라는 것입니다. CLAUDE.md, 스킬, 메모리, MCP 설정이 그대로 먹고, 트래커 쓰기 범위 같은 권한도 Claude Code의 허용·거부 규칙으로 겁니다.

할 일은 티켓으로 적고, 트래커는 MCP 커넥터로 붙입니다#

할 일은 전부 이슈 트래커 Plane의 티켓입니다. 혼자 쓰면서도 티켓을 두는 이유는 넷입니다.

  • 병렬 작업의 맥락 여러 작업을 병렬로 돌리다 보면 어디까지 했는지 맥락을 놓칩니다. 세션마다 티켓을 읽고 시작하면 그 맥락이 제 머리가 아니라 티켓에 있습니다.
  • 세션은 끝나면 잊음 대화 속 결론은 다음 세션에 닿지 않지만 티켓 본문과 코멘트는 닿습니다. 그래서 제 지침의 첫 줄이 「티켓은 코멘트까지 전부 읽고 시작한다」입니다.
  • 완료 기준 시작할 때 적어 두지 않으면 에이전트가 자기 기준으로 완료를 선언합니다. 9월에 제 티켓 29건을 세어 보니 10건에는 완료를 판정할 문장이 없었습니다.
  • 다음 날 아침의 입력 티켓 코멘트는 아침 브리핑과 개인 위키 갱신이 읽는 재료입니다. 결론을 거기 적어야 다음 날 아침에 돌아옵니다.

트래커로 Linear 대신 Plane을 고른 이유는 요금입니다. Linear 무료 플랜은 워크스페이스 전체에 이슈 250개 상한이 있고, 넘으면 혼자 써도 월 $10짜리 Basic으로 올라가야 합니다. Plane Cloud 무료 플랜은 12명까지 쓸 수 있고 작업 항목 수에는 상한이 없습니다. 제 워크스페이스의 티켓은 1,100개를 넘어서, 혼자 쓰는 개인 용도라면 Plane 쪽이 맞습니다.

에이전트에게 맡기는 티켓은 본문을 네 칸으로 적고, 결정은 코멘트에 쌓습니다.

  • 의도 왜 하는지와, 끝났을 때 무엇을 보면 됐다고 할지
  • 검증 방법 완료의 증거 목록과 누가 언제 확인하는지
  • 사람이 정할 것 에이전트가 정하면 안 되는 판단과 그 선택지
  • 경계 하지 않는 것과 깨면 안 되는 것

Plane이 내주는 원격 MCP 서버를 Claude Code에 로컬로 등록하지 않고 claude.ai의 커스텀 커넥터로 붙인 것이 이 구성에서 제일 중요한 부분입니다. 커넥터는 계정에 붙으므로 Claude Code 세션, 웹, 데스크톱 앱, iPhone 앱이 모두 같은 도구를 봅니다. iPhone에서 티켓을 만들고 서버의 세션이 그 티켓을 집어 가는 흐름이 추가 설정 없이 됩니다. 등록 절차는 커스텀 커넥터 등록 글에 있습니다.

한계도 있습니다. Plane의 작업 템플릿과 작업 유형은 유료 플랜부터라(무료 플랜에서 API로 부르면 HTTP 402) 네 칸 양식을 템플릿으로 강제하지 못하고, MCP로 본문이나 코멘트를 쓸 때 HTML을 여러 줄로 보내면 빈 문단이 생기는 식으로 렌더가 깨집니다. 에이전트에게 맡길 티켓을 어떻게 쓰는지는 트래커가 무엇이든 같은 문제라, 여기서는 네 칸까지만 적습니다.

대화형 세션은 레포 하나에서만 엽니다#

Claude Code의 자동 메모리는 git 레포 단위로 저장됩니다. 저는 작업대 레포, 서버 설정 레포, 개인 위키, 블로그처럼 레포 여럿을 오가며 일하는데, 레포 폴더마다 세션을 열었더니 자동 메모리 파일이 한 레포에 104개, 다른 레포에 37개 식으로 다섯 곳에 흩어졌습니다.

그래서 레포들을 서브모듈로 묶은 상위 레포 하나를 만들고 세션은 그 루트에서만 엽니다. 메모리가 한곳에 쌓이고, 루트의 CLAUDE.md 한 장이 레포 지도 역할을 합니다. 대신 하위 레포의 CLAUDE.md는 세션 시작 때 실리지 않고 그 폴더의 파일을 Read 도구로 열 때만 들어오는 등 함정이 있는데, 다른 선택지와 비교한 것까지 적으면 길어져서 여기서는 넘어갑니다.

걷어낸 기준은 하나였습니다#

무엇을 남길지는 기능이 얼마나 많은가가 아니라 실제로 몇 번 썼는가로 정합니다. 새 도구를 들일 때는 이미 있는 것 위에 얹고, 몇 주 뒤 실제로 몇 번 썼는지 세어 남길지 정합니다. iPhone에서는 원격 제어 하나만 쓰는 것도, 트래커를 기능이 많은 쪽이 아니라 매일 써도 돈이 안 드는 쪽으로 고른 것도 그래서입니다.
